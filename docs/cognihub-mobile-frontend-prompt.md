# Cognihub 移动端前端规划提示词（v2026-05-07）

## 给 LLM 的总体指令

你的任务是为 **Cognihub** 这个个人情报中心项目设计**移动端前端**（手机原生 APK 或微信小程序，技术形态待定）。

**重点：先做布局规划与交互流程，不写代码。** 产物是 Markdown + ASCII 线框图，包含信息架构、页面结构、关键交互、视觉风格规范。

阅读下面的产品上下文，然后按"产出格式"逐节输出。

---

## 产品上下文（必读）

### 一句话定位

把碎片化的外部信息（新闻、B 站视频、用户笔记）聚合成"主题—事件—来源"三层结构的个人情报中心。所有结构既能被 AI 自动维护、也能被用户在编辑器里手动改。

### 数据模型

四类对象，前三类同构（标题 + 内容文本对象）：

- **主题 (Topic)** — 大颗粒，用户关心的领域（"OpenAI"、"机器人与具身智能"），17 个量级
- **事件 (Event)** — 中颗粒，一个具体可命名的发生（"宇树赴美参展受阻"），1000+ 量级
- **笔记 (Note)** — 微颗粒，用户私域沉淀，任意目录结构
- **原始数据 (SourceItem)** — 不可变，来自新闻爬虫 / B 站视频 / 用户手工录入，10000+ 量级

主题与事件多对多（一事件可挂多主题）。事件与原始数据多对多（一事件挂多个 source）。

### 当前桌面端三大页面

1. **看新内容（FeedPage）** — 主题胶囊 + 事件流。点开事件看详情、关联 source、用 AI 联动找 source、用 AI 重写
2. **整理笔记（NotesPage）** — 文件树 + 编辑器。同时管本地目录和 SSH 远程目录。每个文件都能"AI 联动"找 source 然后行级 diff 接受修改
3. **信息源（SourcesPage）** — UP 主订阅管理 + 原始数据浏览（视频附 Whisper 转写全文）

### 关键 AI 能力（移动端必须保留可见性）

1. **联动**：给某个事件 / 主题 / 笔记，跑 reranker 找强相关的 source 自动入库
2. **派生**：给某个主题，从全库 source 里聚出相关事件（增量：已有事件就挂入，没有就新建）
3. **重写**：给某个笔记，结合相关 source 用 LLM 输出建议修改，行级 diff
4. **结合来源**：给某个事件，让 LLM 阅读关联 source 重写事件标题/描述

所有 AI 操作都是**异步任务**（后端跑），有进度有取消按钮，可以离开页面后回来看结果。

### 用户场景

主用户是**信息密集型职业**（产品 / 投研 / 程序员等），他们的典型动作：

- **早起 5 分钟**：扫一眼"新闻 / B站 / 笔记 各更新了多少"，挑感兴趣主题点进去看新事件
- **通勤路上**：刷主题流，给某些事件加个收藏 / 转发到笔记 / 临时备注
- **碎片时间**：看到某条不错的新闻，标记"这条挺有意思，等下回到电脑前想细看"
- **晚间整理**：在笔记区某文件下点 "AI 联动"，让 AI 把今天新出的相关 source 整合进来，自己审一下 diff

**手机端不需要做"完整笔记编辑"**——长文输入手机不合适。手机端核心是**消费 + 标记 + 触发**，深度编辑回到桌面端做。

### 桌面端不可直接搬到手机的几个东西

- **NotesPage 文件树左侧 + 编辑器右侧** — 屏幕宽度不够
- **EventDetailPanel 抽屉从右侧划入** — 手机要全屏 push
- **TopBar 5 个 indicator 横排** — 手机宽度只够放 1-2 个
- **多 LLM provider 切换 / 设置面板** — 手机版要么不放、要么塞二级页面

## 产出格式（逐节输出）

### 第 1 节：信息架构（IA）

画一张层级图，描述移动端的所有页面 + 它们的从属关系 + tab 结构。

要求：
- 用 markdown 列表 / 树状缩进表示
- 每个页面注明：作用一句话 + 是否在 tab bar 上 + 进入路径
- 跟桌面端三页面（看新内容 / 整理笔记 / 信息源）做一个映射表

### 第 2 节：底部 Tab Bar

手机端用 tab bar 做主导航。给出：
- tab 数量（建议 3-5 个）
- 每个 tab 的图标语义（不画 SVG，描述）+ label
- 哪些功能不进 tab bar、走二级页面（理由）

### 第 3 节：每个主页面的线框图

对每个 tab 主页面，给出：
- ASCII 线框图（手机竖屏比例 ~360x640）
- 页面分区说明（顶栏 / 主区 / 底栏 / 浮动按钮）
- 滚动行为（哪些区固定、哪些区滚）
- 关键元素的视觉权重（最显眼的是什么、其次是什么）

至少包含：
- **首页 / Feed**（看新内容 移动版）
- **主题详情**（点击主题胶囊后的页面）
- **事件详情**（点击事件卡后的页面，含 AI 操作触发）
- **笔记列表**（笔记区简化版）
- **笔记详情**（含 AI 联动 + diff 简化交互）
- **信息源列表 / 信息源详情**

### 第 4 节：核心交互流程

给出**至少 5 条**完整的用户旅程，每条用步骤列表 + 简短线框图描述：

1. **早起浏览**：打开 → 看到 "新闻今天 +120 / B站 +5"  → 点某主题 → 看新事件 → 点开看详情
2. **触发主题派生**：用户进主题详情 → 点重新派生 → 看进度 → 通知 / 回来看结果
3. **触发笔记 AI 联动**：用户在笔记详情 → 点 AI 联动 → 回到列表（任务在后台跑）→ 完成提醒 → 进入 diff 审阅
4. **diff 审阅**：在小屏上单条接受/拒绝（这是难点，特别说明手势）
5. **手动挂 source 到事件**：事件详情 → 搜索 source → 选中 → 挂入

### 第 5 节：异步任务的状态可见性

桌面版有 TopBar 多个 indicator。手机端必须重新设计：
- 任务进行中如何让用户感知（顶部 banner？通知中心？小红点？）
- 任务结束如何反馈（推送？徽章？）
- 用户如何取消（在哪个页面、什么手势）
- 多任务并发时怎么排队展示

### 第 6 节：视觉风格

桌面版是**深色赛博朋克**风格（cyan 主色、深紫 / 深蓝 / 深灰背景、abstract glow shadow）。
评估手机端是否沿用，给出建议：
- 如沿用：注意手机阅读疲劳的调整（增大对比 / 减少 glow 等）
- 如调整：给出新方向（warm dark / minimalist light / 其他）

提供色板规范（主色、辅色、强调色、状态色 success/warning/error/info、背景层次）

### 第 7 节：交互手势规范

手机端要明确（每条 1 句话 + 一个适用场景）：
- 长按用来干什么
- 滑动（左/右）用来干什么
- 下拉刷新触发什么
- 双击 / 双指捏合是否使用

### 第 8 节：技术形态对比与建议

**这一节最后写**。基于上面的设计需求，给出：

| 技术形态 | 优势 | 劣势 | 适配性评分 |
|---|---|---|---|
| 微信小程序 | 触达快、无需安装 | 限制多、文件 IO 受限、无法本地存储大文件 | ?/10 |
| Capacitor / Tauri Mobile（同 React 复用） | 与桌面共代码 | 包体大、性能 ok | ?/10 |
| Flutter（重写一遍） | 性能好 | 学习成本、人力多 | ?/10 |
| React Native | 跟前端栈复用多 | 需要原生壳 | ?/10 |
| **PWA**（响应式 + Add to Home Screen） | 零额外开发、复用现有 React + Vite | 无原生通知、ios 受限 | ?/10 |

给出推荐 + 一句话理由。

### 第 9 节：移动端能不能砍掉的功能

桌面有但手机端**故意不做**的清单。每条说明为什么砍。

例如：
- ✗ NotesPage 添加新项目（特别是 SSH 远程） — 手机配 SSH key 流程过重
- ✗ Settings 里编辑 LLM provider key — 输入 sk-xxx 太长，且可能引发安全担忧

### 第 10 节：开放问题

列出 5-10 个**需要用户做产品决策**的开放问题（每条带建议默认值）。

例如：
- 手机端是否做"快速备注"功能（看到某条 source 立刻输几个字成笔记）？建议：做，因为这是手机相对桌面的独特价值
- 主题派生这种 1-2 小时的任务，手机端怎么处理？建议：起任务后允许关页面，靠系统通知召回

## 风格要求

- **不要写代码**，只写产品 / 设计层面的规划
- **每个建议给理由**，不要一句话决定
- **保持事实诚实**：哪些桌面功能不可直接搬要明说
- **优先简单**：手机端少即是多，能砍则砍
- **避免空话**：不要"丰富的交互体验"这种描述，要"长按事件卡进入多选模式"这种具体动作
- 总长度 1500-2500 行，结构清晰可被开发者逐节查阅

---

## 不要做的事

- 不要现在就推荐 React Native vs Flutter（留到第 8 节）
- 不要做视觉稿（你不能画图，但 ASCII 线框可以）
- 不要塞太多假数据，1000 个 mock event 就够示意
- 不要假设用户已经登录 / 多用户场景（cognihub 是单用户产品）
